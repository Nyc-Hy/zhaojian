# 技术路线选型

状态：服务端技术栈已定案；客户端平台仍待验证

原则：先验证“用户是否愿意按建议移动和拍摄”，再承担完整双端成本。

## 1. 客户端候选方案

| 方案 | 优点 | 主要代价 | 适合阶段 |
| --- | --- | --- | --- |
| Android 原生：Kotlin + Jetpack Compose + CameraX | 可低成本分发测试包；相机与权限控制直接；中国设备覆盖广 | 机型、传感器方向和系统版本碎片化 | 小范围实地验证 |
| iOS 原生：Swift + SwiftUI + AVFoundation | 设备矩阵较可控；相机体验一致；商业付费链路成熟 | 上架需要开发者计划；需要 Mac 和真机测试 | 体验打磨与商业化 |
| Flutter | 一套 UI 覆盖双端；本项目只需要参考图采集，跨平台可行性较高 | 相机、EXIF、权限和性能问题仍需写原生桥接 | 产品成立后的双端扩展 |
| PWA / 响应式 Web | 迭代最快；适合验证分析结果的表达方式 | 相机控制、文件元数据、离线和商店分发能力弱 | 最早的可用性原型 |

## 2. 当前建议

采用“两步决策”，暂不把平台写死：

1. **验证原型**：做一个可安装或可打开的轻量原型，完成“导入一张参考图 → 必要时回答一个澄清问题 → 返回 2～5 种有依据的观看可能与现场试法，或明确告知没有足够可靠方向 → 展开技术建议”的闭环；不得为了数量改写相同方向凑数。
2. **首个正式客户端**：根据 10–15 名种子用户的真实设备占比选择 Android 或 iOS 原生；当产品留存得到验证后，再评估 Flutter 或第二套原生客户端。

如果种子用户没有明显平台偏向，优先 Android 内测：无需先承担 App Store 年费，APK 分发更适合早期封闭测试。但这只是验证成本选择，不代表最终产品只做 Android。

## 3. 服务端建议基线

| 层次 | 建议 | 说明 |
| --- | --- | --- |
| API | ASP.NET Core 10 Minimal API | 团队熟悉的长期技术栈；使用内置 DI、ProblemDetails、健康检查、请求超时和限流建立多用户控制面 |
| 数据库 | 当前 EF Core + SQLite；多实例阶段迁移 PostgreSQL | 已持久化账号、任务、结果、用量和分析图元数据；保持数据访问边界便于迁移 |
| 图片存储 | 当前去元数据分析图随 SQLite 单体部署保存；规模化时迁移中国区 OSS/S3 兼容存储 | 不保存原图；资源所有权校验与删除语义保持不变 |
| 模型 | Provider Adapter + 通义千问视觉模型 | 见 `../03-ai/model-strategy.md` |
| 参数计算 | 无副作用的独立规则库 | 可同时被移动端、服务端和测试工具调用 |
| 监控 | 结构化日志 + 请求链路 ID + 成本台账 | 不记录原图、精确位置和完整提示词中的个人信息 |

React/Vite Web 与 ASP.NET Core API 独立构建和部署，通过稳定 `/api/v1` 契约协作。浏览器负责原图处理、预览、本地器材与笔记；后端负责不可信输入校验、身份与权限边界、配额和费用、模型编排与供应商密钥。参数引擎继续是前端可离线运行的确定性 TypeScript 包，不迁入模型后端。

## 4. 必须先做的技术验证

- 同一张图在旋转、压缩和去除 EXIF 后仍能正确分析。
- 视觉模型能稳定输出符合 Schema 的中文 JSON。
- 手机等效焦段能够映射到用户相机的实际焦段。
- 参数引擎在低光、手持、上三脚架和使用 ND 时给出可解释结果。
- 删除原图后，日志仍足以定位失败原因，但不能还原用户画面。
- 弱网和模型超时不会让用户丢失已填写的器材与意图。

## 5. 平台定案门槛

满足以下条件后再锁定首发平台：

- 至少 10 名目标用户完成一次真实外拍测试。
- 超过一半测试者愿意在第二个场景再次使用。
- “建议太泛”“过程太慢”“不愿上传照片”三类问题已有数据。
- 已确认首批用户的手机平台、相机品牌和常用镜头分布。
- 已做一次端到端成本测算，包括模型、服务器、签名、商店和测试设备。
