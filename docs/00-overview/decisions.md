# 决策记录

最后更新：2026-07-24

## 已决定

| 编号 | 决定 | 理由 |
|---|---|---|
| D-001 | 项目工作名称为“照见 / Zhaojian” | 强调人的观看，而不是 AI 侦察和指挥 |
| D-002 | 第一版聚焦风景与日常环境摄影 | 与真实痛点一致，避免退化成人像摆位工具 |
| D-003 | AI 建议不显示审美总分或最佳排名 | 摄影具有主观表达，不应制造唯一答案 |
| D-004 | 构图灵感与技术参数分层展示 | 先保护感受，再按需展开技术 |
| D-005 | 大模型不直接生成最终曝光参数 | 参数必须可验证，由确定性引擎计算 |
| D-006 | 第一版是相机伴侣，不直接遥控相机 | 避免品牌 SDK、连接协议与机型适配吞噬 MVP |
| D-007 | 先支持单张参考图，短视频分析后置 | 控制成本与交互复杂度，先验证核心价值 |
| D-008 | 中国大陆模型基线优先 `qwen3.7-plus` | 支持图片、视频、结构化输出且国内可用 |
| D-009 | 模型必须通过供应商适配器接入 | 允许后续切换 `qwen3.6-flash`、混元、豆包或国际模型 |
| D-010 | 本地离线保留器材、焦段、参数和笔记能力 | 户外网络不可依赖 |
| D-011 | 原图只在浏览器本地解码，模型只接收去元数据的分析图与最小化现场上下文 | 降低上传耗时、模型图像成本和 GPS/EXIF 泄露风险；避免用第二次模型调用重复提取环境 |
| D-012 | 一次分析曾要求提供 4～5 个不排名方向，每个方向必须包含 2～3 条可执行的现场步骤；方向数量现由 D-013 调整 | 当时的实测反馈表明 3 个方向覆盖不足，抽象描述也难以转化为取景行动；后续继续实测发现强制数量会稀释质量，因此保留现场步骤要求、调整数量策略 |
| D-013 | 场景分析改为“画面理解 → 观看方向”两阶段；方向数量曾调整为默认 3 个、确有新取舍时扩展到 4～5 个，现由 D-030 继续收紧为 2～5 个或明确无方案 | 真实试用表明，强制凑足方向会稀释质量，一次调用同时承担识别、解释和行动也容易产生泛化建议 |
| D-014 | 信息不足时先追问一个与当前照片有关的问题；每个方向必须列出具体画面元素、元素关系和它与用户吸引点的联系 | 用户需要的是对当前照片有依据的观看启发，而不是可套用到任意照片的通用构图话术 |
| D-015 | 本地记录“有启发 / 太泛 / 识别不对”反馈，不上传原图或反馈内容 | 用真实照片衡量建议价值，同时保持 MVP 的本地优先和隐私边界 |
| D-016 | 方向卡片直接显示浏览器本地裁切并放大的取景预览；优先采用模型给出的 `suggested_crop`，缺失时依据建议的视角宽窄、画幅方向和已有关注区域做确定性范围模拟；方向详情同时显示预览效果与它在完整原图中的位置 | 只在完整原图上画取景框，或在模型漏给取景框时回退成完整原图，都会让不同方向看起来像同一张照片；明确标注来源的双层预览既让差异可见，也避免把本地模拟冒充最终成片 |
| D-017 | 建立独立运行时控制层，统一管理 Provider 调用、标准化、Schema/业务校验、最多一次修复、脱敏追踪与固定场景验证；原 TypeScript harness 已由 D-023 的 ASP.NET Core 服务与集成测试取代 | 运行策略不能散落在 HTTP 路由、Provider 和 UI 中；统一控制层让供应商、协议和确定性模块可以替换，同时保留同一套验收入口 |
| D-018 | “审美质量”不实现为照片评分，而拆成方向是否具体、是否形成不同观看假设、是否给出可观察实验、是否明确失去什么；自动 harness 只拦截套话、构图公式和无依据的象征叙事，最终价值现按 D-042、D-045 由真实使用中的自然反馈校准 | 当前输出可以通过 Schema 却仍然空泛；单一审美分会重新把 AI 变成裁判，而可核验的质量维度既能推动模型改进，也保留人的感受和选择 |
| D-019 | 画面理解增加可核验的视觉关系，观看方向增加视觉组织策略；前三个方向必须分别采用不同策略，且不能只把同一对元素机械改写为重叠、分离和相切 | 仅清除套话只能得到合规的几何排列，无法形成有价值的观看差异；先识别遮挡、层次、尺度、重复、线条、明暗和色彩骨架，再从不同组织方式生成方向，才能让建议改变观看顺序而不是只换措辞 |
| D-020 | 除整次分析反馈外，在方向详情本地记录“值得试一次 / 还不够具体 / 画面依据不对”，只保存分析编号、方向编号、视觉策略和选择 | 整体“有启发”无法判断是哪一种观看组织产生价值；按方向记录才能用真实使用证据改进提示词，同时不保存照片、标题或用户原话，也不把个人选择变成审美排名 |
| D-021 | 每个观看方向增加一个同时点名至少两个具体元素、只比较一个可见变量的开放“观看问题” | 只有结论和步骤仍容易让用户变成 AI 建议的执行者；可在取景器中比较的问题把审美判断重新交给摄影者，也让方向能被现场证伪 |
| D-022 | 同一分析图和观察上下文可在 Provider 内短时复用已经通过校验的结构化画面理解；不缓存图片，创作取舍变化仍重新生成方向 | 两阶段调用提升了可靠性，但重复试方向时不应再次上传和识别同一张图；结构化短时缓存减少等待，同时不把图片扩大为新的持久化资产 |
| D-023 | 应用后端迁移为 ASP.NET Core 10 Minimal API，React/Vite 前端继续独立构建；HTTP 契约、模型适配器、运行时编排、校验、用量计量和账号数据归后端，器材参数引擎、原图处理、预览与离线副本归前端 | .NET 10 是团队熟悉且可长期维护的服务端技术栈；明确职责后，身份、权限、限流、费用和多实例部署可在后端演进，不把模型密钥或运营规则放进浏览器 |
| D-024 | 浏览器把不超过 60 MiB、6000 万像素的 JPEG/PNG/WebP 原图重新编码为最长边不超过 2048px、文件不超过 2 MiB 的 JPEG 分析图；后端只接受该 JPEG，并再次校验 2 MiB、文件头、完整 JPEG 尺寸和像素边界，不负责展示或二次压缩 | 压缩与预览属于客户端体验，服务端边界属于不信任输入后的防护；双层校验既减少带宽和模型成本，也避免把恶意客户端绕过前端限制后直接交给模型 |
| D-025 | ASP.NET Core 主机统一承载请求 ID、ProblemDetails、请求超时、按客户端/IP 限流、分析并发保护和用量计量接口；身份、配额与费用持久化通过服务接口隔离 | 朋友共享与后续多用户部署不能依赖单进程临时约定；先建立稳定控制面，再把内存实现替换为 PostgreSQL/Redis，不修改场景分析业务契约 |
| D-026 | 个人账号使用 ASP.NET Core Identity、同源 HttpOnly Cookie 与 CSRF Token；分析、任务、图片和用量接口默认要求登录，授权采用策略与资源所有权校验 | 浏览器不保存长期 Bearer Token；认证回答“是谁”，资源授权继续检查“是否拥有这条任务/图片”，避免只凭不可枚举 ID 充当权限控制 |
| D-027 | 当前单体部署使用 EF Core + SQLite 持久化账号、分析任务、结果和用量；数据访问保持 EF Core 边界，部署扩展时迁移 PostgreSQL，跨实例限流与幂等迁移 Redis | 先得到可备份、可重复查看且重启不丢失的个人数据闭环，同时避免把 SQLite 或本机内存假装成最终多实例方案 |
| D-028 | 参考分析图按“用户 + SHA-256”去重保存，一张图可关联多次分析任务；每次任务保存输入快照、状态、已校验结果、模型版本、耗时、Token 与估算费用，并提供删除入口 | 用户需要比较同一图片在不同意图或时间下的观看结果；图片不在账号间共享，结果不覆盖旧结果，也不对多个结果做审美排名 |
| D-029 | 个人中心聚合个人资料、摄影包、摄影日记和分析任务；摄影包与日记以账号数据库为跨设备事实来源，浏览器保留离线副本，日记只同步去元数据缩略图和结构化文字 | 设备级存储无法满足朋友同时使用和换设备回看；账号绑定解决归属与隔离，同时保留户外断网时的本地可用性并避免上传原图 |
| D-030 | 场景分析只在至少存在两种有充分画面依据且彼此不同的观看方向时返回 2～5 种方案；不足两种时返回 `no_options`、原因与已检查依据，不改写标题、焦段或形容词凑数 | 方向数量应反映画面中真实成立的可能性；明确告知“没有足够可靠方案”比输出相似、空泛建议更诚实，也保留摄影者自行判断的空间 |
| D-031 | 分析请求只提交摄影包 ID；服务端按当前账号读取并清洗完整器材能力，拒绝不存在或不属于本人的摄影包 | 客户端提供的器材参数不可作为授权或确定性计算依据，账号侧事实来源才能保证多人使用时的数据隔离 |
| D-032 | 图片技术上下文区分 `original_exif` 与 `current_metering`；前者仅在用户同意后发送相机、镜头、焦段、光圈、快门、ISO、曝光补偿和拍摄时间，永不发送 GPS、序列号、作者或编辑历史 | 原图参数可以帮助解释已有画面，但不能代替当前现场测光；白名单与明确来源可避免隐私和错误参数传播 |
| D-033 | 千问两阶段输出使用强制 Function Call，每阶段只能调用指定函数；函数参数 Schema、后置校验和业务规则共同构成边界，修复调用仍强制使用同一函数 | Function Call 改善结构传输但不等于内容可信，仍需独立 Hook、Schema、枚举、范围与业务校验 |
| D-034 | 分析创建改为异步任务：上传和持久化成功后立即返回任务 ID，后台依次更新 `queued`、`understanding`、`generating` 与终态，前端轮询并可刷新后继续查看 | 真实视觉模型可能耗时数十秒；请求长连接不应承担任务生命周期，也不应让刷新页面丢失进度 |
| D-035 | 摄影包允许本人编辑；服务端校验数值边界，并在镜头名称可可靠解析出焦段时提示名称与记录范围不一致，但不擅自覆盖用户记录 | 器材能力是确定性参数计算的事实来源；把矛盾静默带入计算比明确提示更危险 |
| D-036 | 异步任务增加取消请求、租约超时回收和刷新后恢复；取消是终态且不扣成功额度，后台工作必须响应取消令牌 | “异步”不仅是返回任务 ID，还必须允许人结束等待，并在进程异常后给出可解释终态 |
| D-037 | 账号闭环增加修改密码、数据导出与账号注销；本地演示环境的密码重置只签发短时一次性恢复码，不假装已经发送邮件，生产环境必须接入经过验证的邮件发送器 | 账号安全与个人数据权利必须可执行；外部通道未配置时应诚实暴露边界 |
| D-038 | 模型价格采用带生效时间的服务端配置，任务保存计费版本与费用明细；失败、取消和补偿规则单独记录，不把估算费用冒充已扣款 | 模型账单会变化，费用必须可追溯且与用户权益结算分离 |
| D-039 | 去元数据分析图采用可配置保留期，定时清理无任务引用或超过保留期的副本；清理服务只处理可证明属于其范围的记录并留下汇总日志 | 手动删除不足以满足长期最小化保存原则，后台清理必须可审计且不误删日记或账号资料 |
| D-040 | 固定摄影评测集使用版本化清单、结构契约与确定性质量门禁；真实模型执行必须显式开启并单独记录，不进入默认 CI 费用路径 | 提示词与 Function Call 的稳定性不能由单张漂亮样例证明，也不能让 CI 意外产生云端费用 |
| D-041 | 单实例继续使用 SQLite 与进程内队列；跨实例所需数据库、分布式额度/幂等、对象存储和持久任务队列均通过接口与配置隔离，未配置外部基础设施时不得标记为多实例就绪 | 先保留本地可运行性，同时防止把单进程保护误认为生产级分布式保证 |
| D-042 | 第一个大版本定义为“照见 1.0 Skill 基础版”：`1.0.0-beta.1` 交付完整工程与自动训练体系，`1.0.0` 再以真实使用中的自然反馈证明核心价值 | 区分工程能力完备与产品价值已经稳定，避免把内部训练流水线完成直接等同于用户价值成立 |
| D-043 | 画面观察与构图关系能力改为供应商无关、可版本化的 Skill 定义；运行时通过注册表加载，历史任务保存 Skill ID、版本与内容哈希快照 | 专项能力需要可训练、可追踪、可替换和可回滚，同时不能把业务层绑定到单一模型或让历史结果随版本漂移 |
| D-044 | 1.0 首批只交付 `observe-scene` 与 `composition-relations` 两个基础 Skill，继续服务现有现场观看流程；独立构图课程和 Skill 目录后置 | 先提升现有核心闭环的基础能力，避免同时扩张为课程产品和复杂能力市场 |
| D-045 | 离线训练采用 AI Skill Trainer 编排观察、生成、批评、红队和整理角色，训练标注统一视为 `model-suggested`；不建立人工逐图标注团队 | 大模型可以高效完成事实提取、结构检查和候选生成，但不能把自己的审美判断伪装成人工真值 |
| D-046 | 1.0 数据基础统一为 60 张来源明确的真实摄影图片，按 25 张风光自然、15 张城市日常、10 张人物环境、10 张普通或困难照片覆盖，并固定为 36/12/12 的训练、回归与保留集 | 小规模但结构化的数据集足以训练和验证基础能力；固定保留集可防止为通过新版本而移动样例 |
| D-047 | 线上反馈和模型输出不能直接热更新正式 Skill；新经验只能进入隔离候选，经确定性门禁、固定回归、保留集对比与 shadow 后原子发布，并可回滚 | 同时获得预训练和持续演进能力，又阻断脏数据、提示注入、单次异常和模型自我强化对生产能力的污染 |
| D-048 | 个人创作记忆与全局 Skill 经验分离存储；个人记忆必须可查看、修改、删除、关闭和导出，默认不包含原图、完整用户原话、GPS 或模型内部推理 | 个体偏好不等于普遍审美规律，用户也必须保有对个人数据和创作倾向的控制权 |
| D-049 | 1.0 保存可追溯的 `CreativeIntent`，并定义 `FinalPhotoObservation` 与 `PostProcessPlan` 草案，为摄影复盘和后期思路铺垫；本版本不执行自动修图 | 先建立拍摄意图、最终成片观察和后期取舍之间的稳定语义桥梁，避免过早进入不可逆像素修改 |
| D-050 | 真实模型训练和评测必须由开发者显式开启、记录模型与预算，不进入默认 CI；默认验证使用 Mock、固定 fixture 与确定性门禁 | 训练能力需要可复现和可控成本，不能让测试环境意外访问远端模型或产生不可追踪费用 |
| D-051 | 核心分析任务由服务端强制编排所需 Skill：先执行 `observe-scene`，观察结果通过契约后再执行 `composition-relations`；模型和客户端都不能跳过、替换或自行选择这两个阶段 | 核心能力属于产品契约而不是模型偏好；任务创建时固定 Skill 版本与内容哈希，后台只按该快照恢复执行，缺失或不匹配时关闭失败，避免版本漂移和隐式绕过 |
| D-052 | 1.0 的 60 图清单使用 Wikimedia Commons 文件页与开放许可元数据作为首批来源证据；图片只进入本地忽略目录，下载时移除 JPEG APP/COM 元数据，日常恢复严格按冻结清单与哈希执行，只有显式重建命令可以产生新清单 | 来源证据、许可链接、署名和文件哈希必须可追溯，同时不能把 Commons 元数据误当法律保证；将恢复与重建分开可避免外部搜索结果变化后静默污染固定训练、回归和保留集 |
| D-053 | AI Skill Trainer 使用独立于用户分析任务的离线文件检查点；Mock 必须跑完整 60 项五角色流程，但所有 Mock 制品强制标记为不可进入正式训练。真实训练入口在角色 Provider、预算扣减和费用报告完成前保持关闭失败，即使提供密钥也不联网 | 离线训练运行不应污染用户任务数据库；流程演示数据也不能冒充真实照片伪标注。先证明状态机、恢复、取消、隔离和报告边界，再接入显式授权的付费模型，可降低脏数据和意外费用风险 |
| D-054 | 真实 Trainer 通过独立角色 Provider 调用模型，脱敏后的结构化角色结果写入本地 `role-outputs/` 并由检查点引用；五个角色的 Function Schema 只暴露该角色允许返回的字段，适配器只保留 `summary`、该角色结果数组和未知字段，丢弃供应商额外返回的其他已知角色数组，再补齐统一空数组；未知字段、缺失必需结果或类型错误仍关闭失败。Qwen 请求固定关闭思考模式，以 `max_pixels=2621440` 约束观察图输入，以 `max_completion_tokens=4096` 限制供应商侧最大输出，并在联网前拒绝超过 160000 字节的非图片请求载荷。每次调用前获取费用租约；已返回可信 Token 但未通过角色门禁的调用记为 `failed` 并按实际用量结算，缺少可信用量或崩溃遗留的调用才按最大单次费用记为 `uncertain`。候选类型与最终制品使用同一枚举，供应商旧版 `constraint`、`evaluation_case` 只确定性归一为 `validator`，其他未知类型仍拒绝；聚合证据 ID 时确定性去重。预算不足时停止派发并生成拒绝报告。同一 `run_id` 由跨进程锁保证单写，活动运行的取消命令只写取消请求，由持锁进程收口。真实候选仍为 `model-suggested`，在 WP6 门禁和发布完成前一律不可进入活动 Skill | 角色结果必须可恢复、可审计且不能依赖模型内部记忆；角色字段白名单能吸收兼容接口的冗余公共字段，同时不把任意未知结构带入训练制品。统一候选枚举、有限旧值归一和证据去重，避免角色结果已校验但最终制品因合同漂移失败。区分已知失败与费用不确定调用，避免把可核验账目按最坏租约重复放大，同时仍对真正未知的远端状态保守结算 |
| D-055 | 候选发布使用独立 `SkillEvaluationReport` 作为强制证据：同一冻结 60 图的基线与候选训练报告必须具有可比较键，按九个非审美维度分别比较，并逐分区检查固定回归和保留集；成本、平均/最大延迟、严重新增失败、来源与兼容性分别设门禁。服务端发布配置冻结数据集 ID、版本与内容哈希。candidate 评测报告只允许进入 shadow；shadow 观察 ID 必须等于被评测候选报告的运行 ID，该阶段报告才允许激活。每次状态变更必须携带操作者和原因，并把命令、评测报告 ID/哈希与前后状态原子写入注册表审计；报告被修改、越界、字段不全、数值/审计语义异常或门禁失败时，活动版本保持不变 | 评测结果不能只存在于人工判断或可绕过的命令参数中；把不可变证据绑定到状态迁移，既能阻断模型候选直接热更新，又能让发布、停用和回滚复核到具体版本、数据、成本与失败证据 |
| D-056 | 个人反馈使用当前账号设备队列与服务端白名单同步：默认关闭，明确同意后服务端重新核对任务、方向、视觉策略和 Skill 快照；至少两个不同任务的明确枚举信号才形成偏好。去标识化全局候选以源反馈外键保持可删除性，但没有运行时读取入口 | 个人创作倾向需要可积累，也必须能撤回、纠错和隔离。用服务端事实复核、不同任务门槛与候选物理隔离，可以阻断客户端伪造、单次点击和脏数据直接污染正式 Skill |
| D-057 | `CreativeIntent` 由服务端从已校验任务和方向确定性生成，并保存任务 Skill 与摄影包快照；摄影日记只关联意图 ID。来源任务删除时保留契约快照，意图删除时日记回到可空兼容状态；后期仍只定义多方案可逆契约 | 自由文本复制无法解释来源，也会在 Skill 或器材变化后失真。稳定快照把现场选择、复盘和未来后期思路连起来，同时避免把语义桥梁扩张成自动修图 |
| D-058 | `1.0.0-beta.1` 使用独立 `BetaReleaseEvidence` 记录统一版本、命令日志、制品哈希、预算/回滚/kill switch/数据演练、真实浏览器记录与 60 图真实报告。3 图烟测、Mock 或手工通过字段不能进入 `ready`；工程 Beta 与商店、备案、支付、真实设备和公开运营签字分开 | 发布条件必须可重复核验，同时不能把小样本接线证明冒充完整质量结论，也不能用工程测试替代外部合规和运营责任 |
| D-059 | 60 图真实训练允许每个角色最多一次受控修复，整次运行的额外尝试总数最多 15；其中最多 1 个可以是缺少可信用量的上游不确定调用，并按单次租约上界保守计费。未知字段和枚举仍先关闭失败。每个失败或不确定调用都必须标记为可重试，并在同一 `run.json` 中由同资产、同角色、下一次尝试的成功调用闭合。发布门禁仍要求 300 个最终成功角色结果、0 个失败样例和 0 个取消样例 | 真实模型在 300 个角色结果中可能偶发违反结构契约或遭遇一次网络中断；要求所有首轮调用零漂移会把已经受控修复的完整结果误判为不可发布，也鼓励重复整批付费运行。限制修复总量、对不确定费用按最坏值记账并复核逐调用闭环，比放宽枚举、忽略调用或反复整批重跑更可审计 |
| D-060 | 训练 Provider 对观察和方向实行原子级污染隔离：固定摘要只作确定性中性投影；单条观察或方向命中推测、无依据情绪、构图公式、裁判式语言、具体参数或缺少观察引用时，只排除该条并记录 `deterministic_gate` 审计，剩余条目继续进入 critic/red_team。全部条目被排除时仍关闭失败并受有限重试约束；未知字段、类型和枚举不得借此归一 | 真实评测证明，同一次结构化输出中可能同时存在有证据条目和一条修辞污染。整次丢弃会放大费用与随机重采样，直接改写又会隐藏模型问题；原子排除既阻止脏数据进入训练制品，也保留可核验内容和审计证据 |
| D-061 | 方向生成角色升级为内部结构化契约 2.0：模型只选择证据、元素、视觉策略、单一可见变量、变化方式、保留/弱化对象和机位自由度，由确定性中文渲染器投影为现有 `directions`；证据不足时模型必须显式返回 `no_options` 原因码和已检查证据，过滤器不得把失败静默改写为无方案。受控修复只回传枚举失败原因、角色、尝试次数、证据 ID 与排除计数，不回灌原始脏文本。历史失败与样本暴露分别进入带内容哈希的离线语料库和暴露账本；任何已经进入真实调用选择范围的图片都视为已暴露，不能继续冒充未见保留集 | 自由文本方向同时承担观察引用、摄影表达和安全边界，导致模型稍有修辞漂移就整条失败，也让重试重复犯同一种错误。把模型判断与面向人的表达拆开，既保留审计和人的选择空间，又能稳定生成中文方向；显式无方案比“全部被过滤”更诚实。失败语料与暴露账本让改进可重放，并阻止已经看过的保留集产生虚假的泛化结论 |

## 待验证

| 编号 | 问题 | 验证方式 |
|---|---|---|
| Q-001 | 用户更愿意先说一句话，还是先点选“光/形状/空间”等入口？ | 5 人可用性测试 |
| Q-003 | 焦段取景框是否需要首次器材校准？ | 三类手机与两类相机实测误差 |
| Q-004 | 试拍反馈采用导入照片还是拍摄相机直方图更顺畅？ | 原型对比 |
| Q-005 | 首发平台是 Android、iOS 还是移动 Web 验证页？ | 结合目标测试用户设备与开发资源决定 |
| Q-006 | 免费额度和次数包价格如何设置？ | 先测单次成本与付费意愿 |
| Q-007 | 2048px 分析图能否兼顾细节识别准确率、等待时间与单次成本？ | 用同一批相机原图对比 1600/2048/2560px 的识别错误、耗时和用量 |
| Q-008 | 两阶段分析增加的等待与成本，能否换来稳定的具体性提升？ | 固定照片集对比单阶段与两阶段的“有启发/太泛/识别不对”、耗时与调用成本 |
| Q-009 | 视觉策略差异能否提升真实照片中“至少一条值得试拍”的比例，而不是让模型学会新的分类标签？ | 固定保留集做隐藏版本与顺序的新旧对比，Beta 后再观察真实使用中的选择、修改、有启发、太泛和识别不对 |
| Q-010 | “观看问题”能否让用户做出更具体的现场比较，并提高至少一条值得试拍的比例？ | 用同一批真实照片对比仅给结论与加入观看问题的版本，记录选择理由和现场复拍差异 |
| Q-011 | 结构化理解复用能把同图改动创作取舍的等待缩短多少，同时保持观察一致？ | 连续运行同图首轮与二次方向生成，记录画面理解、方向生成和总耗时；再用修改观察事实的请求确认缓存失效 |

## 不在 MVP

- 相机 Wi-Fi/蓝牙遥控。
- 360° 环境扫描和三维重建。
- 精确距离与机位导航。
- 摄影社区、关注、点赞和公开作品排名。
- 自动修图、滤镜和生成式改图。
- 全量相机镜头数据库。
- 个性化模型微调。

MVP 边界保留用于解释当前纵向原型；1.0 的新增范围以[照见 1.0 Skill 基础版开发范围](../01-product/v1-skill-foundation-scope.md)为准。
